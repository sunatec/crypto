# 提案：修正子浪「驱动/调整」判定（legShape 过粗导致假阴性）

## Why

`analyze-wave-manual.js` 里用 `legShape()` 判断一段子浪是「驱动浪形态」还是「调整浪形态」，供单锯齿（a/c 须驱动、b 须调整）、平台形（a/b 须调整、c 须驱动）、双/三锯齿、联合形等手册的**浪型规则**调用。当前实现极其粗糙：

```js
const impulseLike = seg.length >= 6 && seg[0].type === expectedFirstType;
```

它**只数子枢轴个数 + 看首枢轴类型**，完全不检查重叠、不套推动浪规则。而它用的是最细枢轴（`lookback=1`、无 ATR 过滤），于是**任何跨度稍大的腿都必然有 ≥6 个子枢轴 → 被无脑判为「驱动浪」**。

真实后果（BTC-USD 1d 实例）：2025-11-21→2026-01-14 的反弹（80524→97963）内部是 9 个重叠摆动、反复冲击同一价区，明显更像复杂调整；但 `legShape` 因其子枢轴够多就判成「驱动浪」，导致 116410→60001 的**单锯齿假设被错误否定**（`zigzag.pattern.b-is-corrective` 误判 b 浪为驱动）。这是一个把「长/复杂」等同于「推动浪」的**假阴性**。

## What Changes

在 `analyze-wave-manual.js` 内（不改老脚本 `analyze-kline-wave.js`）：

1. **重写 `legShape` 的 `impulseLike` 判定**：从「数枢轴」改为**真正尝试推动浪验证**——在该腿的子枢轴上滑动 6 点窗口套 `buildImpulseStrictManual` / 楔形手册，只有当**存在一个通过全部规则的推动浪/楔形**时才判定为「驱动浪形态」；否则视为「调整浪形态」。
2. **重叠即否定的兜底**：即便凑不齐 6 点窗口，若该腿内部出现明显重叠（子浪回撤突破前一同向子浪起点），也倾向判为调整浪。
3. 保持 `abcLike`、`swingCount` 等既有字段兼容；仅收紧 `impulseLike` 的语义。
4. 递归深度限制为 1 层（子枢轴上只做一层推动浪校验，不无限下钻），避免性能与复杂度失控。

## Impact

- 修改：`analyze-wave-manual.js` 的 `legShape`（及必要的辅助）。
- 影响面：所有依赖「a/b/c/w/x/y 是否驱动浪」的手册规则——单锯齿、双/三锯齿、平台形三子类、联合形。预期减少「长复杂调整腿被误判为驱动浪」造成的假阴性。
- 回归：需确认既有 33 个单测仍通过；新增针对「重叠复杂腿应判为调整浪」的用例；对 BTC-USD 1d 重跑，确认 116410→60001 的单锯齿假设不再因 b 浪误判而被淘汰（若仍被淘汰，应是别的规则，且理由可解释）。

## 非目标

- 不做多层递归数浪（只做一层子结构校验）。
- 不改度量层、否定法引擎、报告结构、CLI。
- 不承诺「修完后 116410→60001 一定成为主选」——只保证其淘汰/幸存由**真实规则**决定，而非 `legShape` 的计数假象。
